    In a nutshell

    Every implementation of the client's DevOps platform needs the same four customer documents, and consultants wrote them by hand from a blank page. We built the Implementation Execution Portal, the third system in a services chain we delivered for the client. It takes the signed SOW and the completed readiness checklist, generates Requirements, Solution Design, Implementation Runbook and User Documentation grounded in the client's own knowledge, and supports consultants with five specialist AI assistants, an AI Review Center and live management reporting.

    Client data protectedNames, engagements and screens on this page are sanitised or changed. The workflow is real; the data is not.
    01 · The problem

    Every engagement started on a blank page

    Four documents per engagement, written by the same consultants who were running the implementation. Every section meant hunting across disconnected sources. Watch one section get written both ways.

    Solution Design · EBSSource Code Management
    Illustrative simulation of one section
    What was going wrong
    • Blank page, four times over: Requirements, Solution Design, Runbook and User Documentation, hand-written on every engagement.
    • Quality drifted: structure and depth varied between consultants and between engagements.
    • No traceability: nothing linked a written section back to product docs, the signed SOW or the customer's checklist.
    • Version risk: guidance could quietly come from the wrong platform release.
    • Questions buried in prose: open items weren't tracked to resolution.
    • No portfolio view: leadership couldn't see what was drafted, reviewed or approved, or what it cost.

    02 · The data chain

    From signed contract to delivered documentation

    The portal is the third system we built for the client. It sits downstream of the SOW Generator and the Implementation Readiness Checklist, and all three share one PostgreSQL database. Step through what flows along the chain.

    Read-only upstreamThe portal reads SOW and checklist data through a controlled database function and stores a snapshot. It never writes back to the systems that own the contract.

        09 · Security and governance

        Credentials never touch the portal

        Enterprise identity at the front door, every model call brokered through n8n, and every action attributed to a consultant, an AI agent or a system process. Trace a request.

        Append-only audit trail
        Governance built in
        • Microsoft Entra ID SSO: sign-in restricted to the client's accounts.
        • Deny by default: network-level middleware blocks every route, plus an auth guard on every API route.
        • Keys stay in n8n: the portal holds no Anthropic or OpenAI credentials and makes no direct provider call.
        • Isolated data: portal data lives in its own schema; upstream SOW tables are read-only.
        • Attributed actions: every event is recorded against a user, an AI agent or a system process.
        • Self-hosted: Docker with nginx TLS termination, on the client's own infrastructure.
