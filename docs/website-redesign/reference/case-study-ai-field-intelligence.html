    In a nutshell

    The client's mobile platform lets technicians capture structured data at the point of work (inspections, maintenance, installations, health, safety and compliance) for more than 1,500 customers worldwide. Its strategy is to move from a workflow engine to a field intelligence platform, and plain-language answers are the centre of that move. We were engaged to build the AI summary feature for its top two tiers: a summary of every completed submission in near real time, and a daily pulse per form, accurate on thousands of forms that every customer designs differently.

    Client data protectedThe client and its people are anonymised. Every form, site, submission and summary in the demos is fictional; the platform statistics and scores are the measured ones. The engineering is real; the data is not.

    01 · The problem

    The answers exist. Nobody has time to read them.

    Technicians file tens of thousands of forms a day, and the knowledge in them (which asset keeps failing, where rework comes from, where a compliance gap is forming) stays locked inside individual submissions. We profiled 90 days of production before designing anything.

    02 · Why it is hard

    Writing a summary is easy. Writing a correct one on 12,374 forms is not.

    One wrong number loses the manager. Every challenge below is backed by measured production evidence. Pick one to see the evidence and how we handled it.

    03 · The guiding rule

    Code where it must be exact. A model where judgement is needed.

    Set on day one, this rule shaped the whole system. Counts, values, totals, dates and layout come from code; the model understands forms, condenses free text and writes. Ask both to count the critical findings in a day of 29 records.

    "How many of today's 29 findings are critical?" · true answer: 7
    A model counting

    Usually right. Sometimes not. One miss is enough to lose a manager's trust.

    Code counting

    Exact every time, and almost free.

    04 · The record view · biggest single gain

    Managers think in records, not in questions

    The first version laid the day out by question: every severity in one list, every description in another, so "Critical", "pump seized" and the site sat in three places and the writer could not tell which site had the seized pump. V1 lays the day out by record. Switch between them.

    05 · The form card · the context layer

    One pipeline that understands every customer's form

    Built once per form version by Claude Opus 5 from the definition and sampled submissions, the form card records each question's role, its priority to a manager, which answers mean a problem, and what to lead with. We learned its job is selection, not description. Tap a question.

    06 · Grounded writing

    Every bullet cites its evidence. Code checks every citation.

    The writer receives numbered input lines and must cite the ones it used. Code then checks every number, date, quote and name against those lines, and flags anything that does not match. Tap a bullet to see its evidence, then slip an error in.

      Fictional pulse in the agreed shape: an opening line with counts and window, bold-led bullets with the most serious first, a closing split. Summaries with a failed check are delivered with flags, never silently withheld.

      07 · Evaluation before product

      We built the yardstick with the client, first

      The client's SVP Product and product manager approved 7 daily and 21 per-submission summaries. We split them into 508 checkable facts and tracked each fact through three stages, so every loss pointed at the layer that caused it.

      28evaluation days, 28 different customers
      7 + 21approved daily and per-submission summaries
      508atomic facts: 182 daily, 326 per submission
      ~$3to judge one day, so full regressions are routine
      Noise bandV0 run twice measured a 2 to 3 point spread. A change was kept only if it cleared that band without raising unsupported claims, with the rule written down before the run.
      Two judges, both reportedA strict judge and, from 19 Oct, a lenient one that reads for meaning. Both are applied to every version: the pipeline made the jump, not the judge.
      Untouched daysOnly 3 of 7 approved days were opened during development. The 4 untouched days gained as much, evidence the changes generalise.
      08 · Seventeen iterations in five days

      One change at a time, each one measured

      From 16 to 20 October every change was built behind a switch, scored with the same judges and kept or reverted by a rule set in advance. Tap any point on the daily score to see what changed.

      kept reverted or set aside target 70–80%

      Measured Daily summary score as measured at the time of each iteration. Iterations 13 onward use the lenient judge. Two other ideas (separate select-then-write steps, and cutting sentences by code) were tried and ruled out: both lost facts.

      09 · Architecture and integration

      Push only. The runtime never reads the client's databases.

      The client triggers; the runtime builds. Each request carries the data it needs in versioned JSON contracts we defined, so the client's storage can change without touching the AI layer. Everything runs inside the client's own AWS account. Tap a component, or pick a failure and see what happens.
