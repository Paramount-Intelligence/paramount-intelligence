    In a nutshell

    The client's AI Foundry was growing fast: agents, runtimes and MCP gateways were being deployed across AWS with no central way to find, own or govern them. In a three-week proof of concept we built the AgentCore Registry: ingestion pipelines that discover live agents and gateways automatically, a governance API with a full approval lifecycle, Cognito-based personas enforced on the server, a React catalog, and a GitLab pipeline that deploys with no stored AWS keys.

    Client data protectedAccount numbers, record IDs and demo records on this page are sanitised or changed. The workflow is real; the data is not.
    01 · The problem

    Agents everywhere. A catalog nowhere.

    AI adoption outran governance. Agents and gateways lived across AWS, ownership was unclear, and nobody could say what already existed. Try answering one simple question both ways.

    QIs there an approved agent that extracts data from PDFs, and who owns it?
    Illustrative simulation · sample records
    What was going wrong
    • No central catalog: agents, runtimes and MCP gateways were spread across AWS environments.
    • Unclear ownership: metadata and owners were hard to find, so assets were hard to trust or reuse.
    • Inconsistent governance: approvals happened differently every time, if at all.
    • No standard access control: nothing decided who could see a draft or retire an approved asset.
    • Growing duplication: without visibility, teams risked rebuilding what already existed.
    • Rising complexity: more services, regions and environments with every new initiative.
    02 · Automated discovery

    Ingestion that reads the live estate

    Two ingestion Lambdas scan AgentCore runtimes and gateways, decide what belongs in the registry, and write every eligible asset as a draft record. Extending discovery to every AWS account the client runs is a Phase 2 recommendation. Run a discovery pass.

    How discovery decides
      
      
    • Scope by protocol: A2A and AGUI agents are ingested; HTTP and unknown runtimes are skipped by agreement, and MCP runtimes come in as gateways.
      • 
      
    • Agent cards first: agents that expose a working card become full A2A records with skills and capabilities.
      • 
      
    • Never lose metadata: everything else is stored as CUSTOM with model, gateways, auth and protocol kept intact.
      • 
      
    • Gateways with detail: URL, auth type, tool targets and interceptors are captured for every MCP gateway.
      • 
      
    • No duplicates: each run checks the registry before writing, so re-running is safe.
      • 
      
    • Draft by default: nothing discovered is visible to consumers until it has been approved.

      04 · The governance lifecycle
      
    Draft to approved, and nothing skips a step
    
      
    Every transition goes through the API, which knows who you are and what state the record is in. Approval decides which records consumers can find in the catalog. Switch persona, take an action, and watch the server allow it or refuse it.
    
    
    
    
    
      
    
        
    Acting as
    
        
      
    
      
    
        
    
        
    
      
    
      
    API traffic
    
    
    
    
    Rules the API enforces
      
      
    • One path only: drafts and rejected records are submitted; only pending records can be approved or rejected; only approved ones deprecated.
      • 
      
    • Wrong state, clear answer: any other move returns HTTP 409 with the state the record must be in.
      • 
      
    • Three editable fields: description, tags and additional metadata. Everything else comes from AWS and stays read-only.
      • 
      
    • Rejection loops back: a rejected record can be edited and resubmitted, with the reason in front of the publisher.
      • 
      
    • Admins can fix in review: pending records are editable by admins only; a publisher gets a 403.
      • 
      
    • Consumers see the result: only approved records ever reach the catalog's consumers.
      •

    When an asset changes in AWS: re-running ingestion never writes a duplicate. An agent that starts exposing a card is upgraded to a full A2A record on the next run, and a gateway that gains a description is re-ingested as an MCP record.

      08 · Delivery
      
      Nothing reaches AWS by accident
      
      
      This pipeline deploys the registry platform itself. Agents and gateways reach the registry through discovery, not through this pipeline. Validation runs on every push. A deployment needs a correctly formatted tag and a person pressing play, and authenticates through GitLab OIDC with no stored AWS keys.       What comes next · Phase 2 recommendations Recommended
        
      
      • Single sign-on: Microsoft Entra ID in place of the proof-of-concept Cognito users.
        • 
      
      • Every AWS account: ingest agents across all of the client's accounts with least-privilege cross-account access.
        • 
      
      • Skills as records: add the AGENT_SKILLS type once the skills repository is populated.
        • 
      
      • Manual registration: let publishers register assets directly, not only through ingestion.
        • 
      
      • Notifications and versioning: alert admins when something is submitted, and keep record history.
        • 
      
      • Agent-card standard: every new A2A agent exposes a card, so it is ingested as a full A2A record.
